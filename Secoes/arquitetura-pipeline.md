# Arquitetura do pipeline

O pipeline é composto por três agentes LLM especializados e um consolidador implementado em Python (Figura X). A arquitetura atribui a cada agente uma única responsabilidade (Gulli, 2025). A orquestração foi implementada diretamente em Python, sem uso de frameworks como LangChain ou LangGraph — decisão justificada pelo caráter sequencial e determinístico do pipeline, cujas entradas e saídas seguem esquemas YAML fixos que não demandam abstrações adicionais.

O Agent 1 recebe exclusivamente o texto do requisito (`base_requirement_text`), sem acesso a contexto, glossário ou metadados. Identifica os fragmentos que admitem mais de uma interpretação e os classifica segundo a taxonomia de Pohl (2025), produzindo o atributo `has_ambiguity`. Por ser independente do contexto experimental, executa uma única vez por requisito e seu output é reutilizado nas quatro condições (C0–C3), evitando chamadas redundantes ao modelo.

Quando `has_ambiguity` é falso, o orquestrador substitui o Agent 2 por um bloco sintético determinístico com status `no_ambiguity` e encaminha o requisito diretamente ao Agent 3. Quando `has_ambiguity` é verdadeiro, o Agent 2 é invocado com o requisito, o contexto controlado da condição experimental em curso e o output do Agent 1. Para cada ambiguidade detectada, o Agent 2 atribui um de três status: `resolvable`, quando há evidência suficiente no texto ou no contexto para selecionar uma interpretação; `unresolved`, quando faltam informações para resolver a ambiguidade; ou `false_positive`, quando a confrontação com as evidências disponíveis revela que a ambiguidade reportada não se sustenta — isto é, uma ou mais das interpretações candidatas não têm base no texto. O status global resultante é `fully_resolvable`, quando todas as ambiguidades são `resolvable` ou `false_positive`, ou `unresolved`, quando ao menos uma permanece sem resolução.

Requisitos com status `fully_resolvable` seguem pela rota `structured` e chegam ao Agente 3. Requisitos com status `unresolved` seguem pela rota `signaling`, encerrando o pipeline sem invocar o Agente 3 — a ambiguidade permanece aberta e requer intervenção humana. O Agent 3, quando invocado, recebe o texto do requisito e o output do Agent 2, e produz o requisito estruturado classificado como requisito funcional, requisito de qualidade ou restrição, conforme Pohl (2025) §3.2. Fragmentos com `resolubility_status: resolvable` são substituídos pela interpretação suportada no `final_statement`; requisitos cuja ambiguidade era `false_positive` têm o texto original preservado.

O consolidador é um script Python determinístico que integra os outputs dos três agentes e a decisão de roteamento em um único artefato por execução, persistido em `final_output.json`. É invocado em todas as execuções, independentemente da rota — inclusive em casos `signaling`, cujo registro compõe os dados de análise. O código-fonte completo do pipeline está disponível em Andrade (2026).
